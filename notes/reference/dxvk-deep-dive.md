# DXVK & VKD3D-Proton Deep Dive

## What DXVK Is

DXVK is a **Vulkan-based translation layer** for Direct3D 8/9/10/11, written in
C++ by Philip "doitsujin" Rebohle. Initial release January 2018. Valve sponsored
the author full-time later that year to advance Linux gaming via Steam Play.

It is **not part of Wine** — it's a set of standalone Win32 DLLs that replace
Wine's builtin `d3d8.dll`, `d3d9.dll`, `d3d10core.dll`, `d3d11.dll`, and
`dxgi.dll`. When a game calls Direct3D functions, DXVK intercepts them and
translates them to Vulkan calls instead of routing through WineD3D (OpenGL).

```
Game → D3D8/9/10/11 API → DXVK DLLs → Vulkan → GPU driver → GPU
```

DXVK supports a broad range of Direct3D games ⚠️ (specific percentages are
unverifiable — coverage is game- and driver-dependent). Current stable:
**v2.7.1** (August 2025). Requires **Vulkan 1.3**.

## What VKD3D-Proton Is

VKD3D-Proton is Valve's fork of upstream VKD3D (WineHQ's D3D12→Vulkan layer),
maintained by Hans-Kristian Arntzen. It implements the **full Direct3D 12 API**
on top of Vulkan.

```
Game → D3D12 API → VKD3D-Proton DLLs → Vulkan → GPU driver → GPU
```

**Upstream VKD3D** (shipped with Wine) targets basic D3D12 feature level 12_0
and can run almost no commercial games. **VKD3D-Proton** targets the full D3D12
feature set with aggressive Vulkan extension use — it's what Proton ships and
what makes modern DX12-only games playable on Linux.

As of v3.0 (November 2025), VKD3D-Proton shares its **DXBC shader frontend**
with DXVK, simplifying development for both projects.

Current stable: **v3.0.1** (May 2026). ⚠️ Next release (v3.1) expected to include
`VK_EXT_descriptor_heap` support for further performance gains (prediction based
on development roadmap — may not materialize in that version).

## 1. Architecture — How Translation Works

### Core Mechanism

DXVK and VKD3D-Proton work on the same principle: they are **Win32 DLLs** that
implement the D3D API using Vulkan as the backing graphics API. When Wine loads
a game's `d3d11.dll`, it loads DXVK's version instead of Wine's builtin.

```
D3D11 call (e.g., DrawIndexedInstanced)
    ↓
DXVK intercepts → looks up current state (pipeline, resources, descriptors)
    ↓
Translates to Vulkan commands:
  - D3D11 pipeline state → VkPipeline (cached)
  - D3D11 resources → VkImage/VkBuffer (with appropriate layouts)
  - D3D11 shaders → SPIR-V modules (generated by DXBC frontend at shader-creation time, compiled to GPU-native code at the same point via GPL)
  - D3D11 descriptor bindings → VkDescriptorSet updates
    ↓
Vulkan command buffer submitted to GPU
```

### Key Translation Mappings

| D3D11 Concept | Vulkan Equivalent |
|---------------|-------------------|
| Immediate context | Command buffer (primary) |
| Deferred context | Command buffer (secondary) |
| Pipeline state (blend, rasterizer, depth-stencil) | `VkPipeline` (graphics) |
| Shader bytecode (DXBC) | SPIR-V (via `glslang`) |
| Shader resource view (SRV) | `VkImageView` + combined image sampler descriptor |
| Render target view (RTV) | `VkImageView` in color attachment |
| Depth/stencil view (DSV) | `VkImageView` in depth/stencil attachment |
| Constant buffer (CBV) | Uniform buffer or `VkDescriptorBufferEXT` |
| Vertex/index buffers | `VkBuffer` with vertex/index binding |
| Swap chain | `VkSwapchainKHR` via DXGI |
| Resource barriers (D3D11 nonexplicit) | Explicit `VkPipelineBarrier` (inserted by DXVK tracking) |

### State Tracking

D3D11 uses a massive **stateful context** — the game sets render states,
shaders, resources, and draw calls reference the accumulated state. Vulkan is
**stateless** — pipeline state must be baked into `VkPipeline` objects and
descriptor sets must be bound explicitly.

DXVK bridges this by:
1. Tracking all D3D11 state changes (dirty flags per state category)
2. On draw call, building a pipeline key from current state → looking up or
   compiling a matching `VkPipeline` (cached in a hash table)
3. Updating descriptor sets for currently bound resources
4. Recording draw commands into a Vulkan command buffer
5. Submitting the command buffer on `Present`

This is the core performance difference from WineD3D: DXVK translates to
Vulkan's explicit model once (at pipeline compile time), while WineD3D must
translate the entire D3D state machine to OpenGL state before **every** draw
call.

### Shader Compilation

HLSL shaders arrive as **DXBC bytecode** (the compiled D3D shader format).
DXVK contains a DXBC-to-SPIR-V compiler ⚠️ (originally derived from the SPIRV-Tools/glslang DXBC frontend, but heavily modified; the shared DXVK/VKD3D-Proton frontend since v3.0 is effectively a new implementation) that runs at
**shader creation time** — when the game calls `CreateVertexShader`,
`CreatePixelShader`, etc.

The pipeline:

```
Game calls CreateVertexShader(dxbc_data)
    ↓
DXVK parses DXBC bytecode → extracts input/output signatures, shader body
    ↓
Translates DXBC opcodes to SPIR-V instructions
    ↓
Output: SPIR-V module (stored in memory for later pipeline creation)
```

With **Graphics Pipeline Library (GPL)** support (`VK_EXT_graphics_pipeline_library`,
available since DXVK v2.0 and Vulkan 1.3), the SPIR-V modules are compiled to
GPU-native code at shader creation time, not at draw time. This eliminates the
classic "shader stutter" problem — the cost is paid during loading screens or
menu navigation, not during gameplay.

⚠️ The exact SPIR-V generation path is complex (hundreds of DXBC opcodes must
be translated). The shared DXBC frontend between DXVK and VKD3D-Proton (since
v3.0) means improvements benefit both projects.

### Why Vulkan Is Faster Than OpenGL for This

| Factor | DXVK (Vulkan) | WineD3D (OpenGL) |
|--------|---------------|-------------------|
| State model | Stateless → explicit pipeline objects | Retained state → per-draw validation |
| Shader compilation | SPIR-V (pre-compiled binary) | GLSL (string compile + LLVM) |
| Multi-threading | Command buffer recording on worker threads | Single-threaded context |
| Memory management | Explicit allocation, no hidden copies | Driver-managed, potential copies |
| Barrier handling | Explicit (inserted when needed) | Driver infers from GL state |
| CPU overhead | Low (direct command generation) | High (state translation per draw) |

## 2. Per-Version Breakdown

| DX Version | DLL Provided | Route | Added To DXVK |
|-----------|-------------|-------|---------------|
| **D3D8** | `d3d8.dll` | Routes through D3D9 backend | v2.4 (Jul 2024) |
| **D3D9** | `d3d9.dll` | Direct implementation | Merged from d9vk (2019) |
| **D3D10** | `d3d10core.dll` | Routes through D3D11 backend | Initial release (2018) |
| **D3D11** | `d3d11.dll` + `dxgi.dll` | Flagship implementation | Initial release (2018) |
| **DXGI** | `dxgi.dll` | Shared infrastructure | Initial release (2018) |

### D3D9

- Merged from the standalone **d9vk** project in 2019
- Full feature set: all D3D9 fixed-function pipeline states, vertex/pixel
  shaders 1.x–3.x, multiple render targets, DXT compression, Anisotropic
  filtering
- Software cursor support added in v2.5 (Nov 2024) — renders the cursor via
  Vulkan instead of relying on the OS, fixing invisible cursor in some games
- `d3d9.maxFrameLatency`, `d3d9.maxAvailableMemory`, `d3d9.allowFse` in config

### D3D10

- Implemented as a thin shim over the D3D11 backend
- D3D10 state is translated to D3D11 equivalents internally
- Very few games target D3D10 exclusively — most use D3D9 or D3D11

### D3D11

- The flagship DXVK target — receives the most optimization effort
- Feature level 12_1 (`D3D_FEATURE_LEVEL_12_1`) since v2.0 (Nov 2022)
- HDR support via DXGI color space negotiation since v2.1 (Jan 2023)
- D3D11On12 support added in v2.2 (May 2023) — allows running D3D11 games
  on top of D3D12 translation (for when the Vulkan driver lacks features)
- Resource management overhaul in v2.5 (Nov 2024) — VRAM savings up to 1GB
  in some titles
- Memory allocation improvements ongoing

### DXGI

The **DX Graphics Infrastructure** DLL handles:
- Adapter enumeration (GPU selection)
- Swap chain creation and presentation
- Frame statistics and synchronization
- DXGI 1.2–1.6 interfaces (fullscreen, swap chain scaling, etc.)

`dxgi.dll` is always required for D3D10/11. D3D8/9 have their own swap chain
logic and don't use DXGI.

## 3. VKD3D-Proton — D3D12 to Vulkan

### Architecture

VKD3D-Proton implements the **Direct3D 12 API** on top of Vulkan. D3D12 is
already a low-level, explicit API (like Vulkan), so the translation is more
direct than DXVK's D3D11→Vulkan. The mapping:

| D3D12 Concept | Vulkan Equivalent |
|---------------|-------------------|
| Command list | Command buffer |
| Command allocator | Command pool |
| Root signature | Pipeline layout |
| Pipeline state (PSO) | `VkPipeline` |
| Descriptor heap | Descriptor pool/set |
| Resource (buffer/texture) | `VkBuffer`/`VkImage` |
| Resource barrier | `VkPipelineBarrier` |
| Fence | `VkFence` / `VkSemaphore` |
| Query heap | Query pool |

### Feature Set

VKD3D-Proton aggressively uses modern Vulkan extensions to match D3D12
features:

- **Ray tracing**: `VK_KHR_ray_tracing_pipeline` + `VK_KHR_acceleration_structure`
- **Mesh shaders**: `VK_EXT_mesh_shader`
- **Variable rate shading**: `VK_KHR_fragment_shading_rate`
- **Work graphs**: Experimental in v3.0 (D3D12's work graphs for GPU-driven rendering)
- **FSR4**: AMD FidelityFX Super Resolution 4 via cooperative matrix + float8
  extensions (v3.0)
- **DLSS3 Frame Gen**: Via dxvk-nvapi integration
- **AMD Anti-Lag**: v3.0
- **HDR**: Full HDR10 support

### VKD3D-Proton vs Upstream VKD3D

| Aspect | Upstream VKD3D (WineHQ) | VKD3D-Proton (Valve) |
|--------|------------------------|----------------------|
| Feature level | Basic 12_0 | Full 12_0/12_1/12_2 |
| Games playable | Very few (basic samples) | Hundreds of DX12 titles |
| Vulkan extensions | Conservative | Aggressive (latest extensions) |
| Driver requirements | Vulkan 1.1+ | Vulkan 1.3 + specific exts |
| Maintenance | Wine project | Valve full-time |
| Shared DXBC frontend | No | Yes (shared with DXVK since v3.0) |

### Driver Requirements

VKD3D-Proton has **hard** driver requirements — if your Vulkan driver doesn't
support them, games won't run:

- Vulkan 1.3
- Descriptor indexing with 1,000,000+ `UpdateAfterBind` descriptors
- `VkPhysicalDeviceDescriptorIndexingFeatures` fully supported
- `samplerMirrorClampToEdge`, `shaderDrawParameters`
- `VK_EXT_robustness2`
- `VK_KHR_push_descriptor`

Recommended (may become mandatory):
- `VK_EXT_image_view_min_lod`
- `VK_EXT_mutable_descriptor_type`
- `VK_EXT_descriptor_buffer`

| GPU | Minimum Driver |
|-----|---------------|
| AMD (RADV) | Mesa 22.0+ |
| AMD (AMDVLK) | Not recommended; use RADV |
| NVIDIA | Vulkan beta driver 515.x+ |
| Intel (ANV) | Mesa 22.0+ |
| **VMware SVGA II** | **No Vulkan support — cannot run** |

## 4. Shader Compilation & State Cache

### Pre-GPL Era (DXVK < 2.0)

Before `VK_EXT_graphics_pipeline_library` (GPL), Vulkan pipelines had to be
created at draw time. When a game first encountered a shader+blend+rasterizer
combination, DXVK would compile the full pipeline synchronously — this caused
**visible stutter** (hitches up to hundreds of milliseconds).

To mitigate this, DXVK introduced the **state cache**:

```
Game session 1: compile stutter, save .dxvk-cache file
Game session 2: load cache → pipelines pre-created → no stutter
```

The state cache (`<game>.dxvk-cache`) is a portable binary format that survives
driver updates and most DXVK updates. It's stored in `$DXVK_STATE_CACHE_PATH`
(default: `$LOCALAPPDATA/dxvk/` on Windows/Wine, `$XDG_CACHE_HOME` or
`$HOME/.cache` on Linux).

### GPL Era (DXVK 2.0+, 2022)

`VK_EXT_graphics_pipeline_library` splits pipeline creation into **fast**
(linking) and **slow** (compilation) parts. DXVK compiles the per-shader parts
when the game calls `CreateVertexShader`/`CreatePixelShader` — during loading
screens or level transitions — and only links them at draw time, which is near-
instant.

**Result**: Shader compilation stutter is **eliminated** in most games. The
cost shifts from first-encounter draw time to shader-creation time (loading).

Tradeoff: Games that load shaders at draw time (many Unreal Engine titles) may
still see some stutter on first playthrough, but it's much less severe. Monitor
with `DXVK_HUD=compiler`.

### Async Shader Compilation (Forks, Now Obsolete)

Before GPL was widely available, **dxvk-async** (a community fork) solved
stutter by returning a dummy shader immediately and compiling the real shader
on a background thread. The game would see garbage for a frame or two instead
of hitching.

This approach was:
- Not merged into mainline DXVK (could cause graphical corruption)
- Detected by some anti-cheat systems (binary differs from upstream)
- Superseded by GPL in DXVK 2.0+

The **dxvk-gplasync** fork exists for older GPUs/drivers that lack GPL
support. It re-enables async compilation via `dxvk.enableAsync=True` in
`dxvk.conf`. ⚠️ Removed from gplasync in v2.7 due to legacy state cache
removal; the config option was changed to `dxvk.enableAsync` with a new
implementation.

### State Cache Today

Even with GPL, the state cache is still useful:
- Caches pipeline **linking** results (faster subsequent loads)
- Valve distributes pre-built state caches for popular games on Steam Deck
- Survives DXVK updates and driver updates (portable format)
- Disable with `DXVK_SHADER_CACHE=0`

## 5. Configuration (dxvk.conf)

DXVK is configured via a text file. By default, DXVK looks for `dxvk.conf` in
the game's working directory. Override with `DXVK_CONFIG_FILE`.

### Per-App Overrides

```ini
[game.exe]
dxgi.maxFrameLatency = 1
d3d9.maxFrameLatency = 1

# Options only apply to game.exe
# Other executables ignore these
```

### Key Configuration Options

#### Latency & Framerate

| Option | Values | Effect |
|--------|--------|--------|
| `dxgi.maxFrameLatency` | 0–16 (default 0) | Limits queued frames. `1` = lowest input lag |
| `d3d9.maxFrameLatency` | 0–16 (default 0) | Same for D3D9 |
| `dxgi.maxFrameRate` | Any integer | Frame rate limiter |
| `d3d9.maxFrameRate` | Any integer | Frame rate limiter for D3D9 |
| `dxvk.latencyTolerance` | ms (default 1000) | Tolerance before latency reduction kicks in |
| `dxvk.latencySleep` | True/False | Custom sleep-based latency control |
| `dxvk.disableNvLowLatency2` | Auto/True/False | Disable NV Reflex (32-bit default: Auto) |

#### GPU Vendor Hiding

Some games have buggy code paths for specific GPU vendors. DXVK can lie about
which GPU is present:

| Option | Default | Effect |
|--------|---------|--------|
| `dxgi.hideNvidiaGpu` | Auto | Report Nvidia as AMD (work around NVAPI crashes in UE games) |
| `d3d9.hideNvidiaGpu` | Auto | Same for D3D9 |
| `dxgi.hideAmdGpu` | Auto | Report AMD as Nvidia (work around AMDAGS issues) |
| `dxgi.hideNvkGpu` | Auto | Report NVK (open Nvidia driver) as AMD |
| `dxgi.customVendorId` | — | Override PCI vendor ID (four-digit hex) |
| `dxgi.customDeviceId` | — | Override PCI device ID |

#### HDR

| Option | Effect |
|--------|--------|
| `dxgi.enableHdr` | Expose HDR10 colorspace to the application. Set this for games that check the "Windows HDR is on" flag |

#### D3D9 Specific

| Option | Effect |
|--------|--------|
| `d3d9.presentInterval` | Override VSync interval. `0` = off, `1` = 60Hz, etc. |
| `d3d9.maxAvailableMemory` | Report a specific VRAM amount to the game |
| `d3d9.allowFse` | Allow fullscreen exclusive mode (lowest latency) |
| `d3d9.deviceLocalConstantBuffers` | Force constants in VRAM (may improve GPU-bound scenarios) |
| `d3d9.modeCountCompatibility` | Limit reported display modes (fixes buffer overflow in old games like AquaNox 2) |

#### Memory & Performance

| Option | Effect |
|--------|--------|
| `dxvk.enableDescriptorBuffer` | Use `VK_EXT_descriptor_buffer` if available (performance) |
| `dxvk.numCompilerThreads` | Threads for shader compilation (default: CPU cores) |
| `d3d11.ignoreGraphicsBarriers` | ⚠️ Skip some resource barriers (faster but may cause corruption) |
| `d3d11.relaxedBarriers` | ⚠️ Looser barrier tracking (performance gamble) |

#### Debug

| Option | Effect |
|--------|--------|
| `dxvk.enableAsync` | Enable async pipeline compilation (gplasync fork only) |

The full reference is in DXVK's repository at `dxvk.conf` (~600 lines of
commented options).

## 6. HUD & Debugging

### DXVK_HUD

Enable with `DXVK_HUD=1` (shorthand for `devinfo,fps`) or `DXVK_HUD=full`.

| Element | Shows |
|---------|-------|
| `devinfo` | GPU name + driver version |
| `fps` | Current frame rate |
| `frametimes` | Frame time graph (recent history) |
| `drawcalls` | Draw calls + render passes per frame |
| `pipelines` | Total graphics + compute pipelines created |
| `descriptors` | Descriptor pool/set usage |
| `memory` | Device memory allocated and used |
| `allocations` | Detailed memory chunk suballocation |
| `gpuload` | Estimated GPU load (may be inaccurate) |
| `version` | DXVK version string |
| `api` | D3D feature level in use |
| `cs` | Worker thread statistics |
| `compiler` | Shader compiler activity (useful for diagnosing stutter) |
| `samplers` | Sampler pair count (D3D9 only) |
| `swvp` | Vertex processing mode (D3D9 only) |
| `scale=x` | Scale HUD by factor x |
| `opacity=y` | Set HUD opacity (0.0–1.0) |

### Logging

| Env Var | Effect |
|---------|--------|
| `DXVK_LOG_LEVEL=none|error|warn|info|debug` | Control log verbosity |
| `DXVK_LOG_PATH=/path` | Write logs to files; `none` disables file logging |
| `DXVK_DEBUG=validation` | Enable Vulkan validation layers |
| `DXVK_CONFIG_FILE=/path` | Custom config file path |
| `DXVK_CONFIG="opt=val;opt2=val2"` | Set config options via env (no config file needed) |

Under Wine, DXVK logs to stderr by default. You'll see per-DLL log files
(`app_d3d11.log`, `app_dxgi.log`, etc.) if `DXVK_LOG_PATH` is set.

### Device Filtering

| Env Var | Effect |
|---------|--------|
| `DXVK_FILTER_DEVICE_NAME="VEGA"` | Use first device whose name contains "VEGA" |
| `DXVK_FILTER_DEVICE_UUID="<32hex>"` | Match by Vulkan device UUID (precise) |

## 7. DXVK-NVAPI

A separate project ([jp7677/dxvk-nvapi](https://github.com/jp7677/dxvk-nvapi))
that implements NVIDIA's proprietary NVAPI on top of DXVK.

### What It Unlocks

- **DLSS Super Resolution** — AI upscaling
- **DLSS Frame Generation** — D3D12 frame interpolation (via VKD3D-Proton)
- **DLAA** — DLSS-based anti-aliasing
- **Ray Reconstruction** — Denoising for ray traced scenes
- **NVIDIA Reflex** — Low latency mode
- **Ansel** — In-game photography
- **DSR** — Dynamic Super Resolution

### How It Works

- Ships as `nvapi64.dll` / `nvapi.dll` (64/32-bit)
- Placed alongside DXVK's DLLs in the wine prefix
- DXVK must be configured to **not** hide the Nvidia GPU:
  ```ini
  dxgi.hideNvidiaGpu = False
  ```
- Game queries NVAPI for DLSS support → dxvk-nvapi intercepts and reports
  support → game enables DLSS → DXVK handles the rendering

Lutris provides a "DXVK-NVAPI" toggle in Runner Options that manages this
automatically.

## 9. DXVK vs WineD3D — Comparison

| Aspect | DXVK (Vulkan) | WineD3D (OpenGL) |
|--------|---------------|-------------------|
| Translation target | Vulkan (explicit, low-level) | OpenGL (retained state) |
| Shader compilation | HLSL → SPIR-V (binary, pre-compiled) | HLSL → GLSL (string, compiled at draw time via LLVM) |
| State overhead | Dirty-state → Vulkan pipeline objects (cached hash table) | Per-draw state machine → GL state calls (hundreds of glEnable/glDisable per draw) |
| Multi-threading | Vulkan command buffers recorded on worker threads | GL context is single-threaded |
| Memory management | Explicit allocation, no hidden copying | Driver-managed (potential wow64_map_buffer copies) |
| Barrier management | Explicit barriers inserted by DXVK tracking | Driver must infer from GL state changes |
| CPU overhead | Low (direct command generation, pipeline caching) | High (state enum translation, GLSL compile, GL call overhead) |
| Driver overhead | Low (modern Vulkan drivers, explicit everything) | High (GL compatibility profile, implicit state) |
| Stutter | Minimal (GPL compiles at load time, state cache for subsequent runs) | Significant (GLSL compile pauses during first gameplay) |
| 1% lows | Typically much better | Often poor |
| GPU requirement | Vulkan 1.3 GPU + driver | OpenGL 4.3+ (any GPU) |
| Anti-cheat flags | Some games detect DXVK DLLs by name or hash | Usually invisible |
| Performance pattern | Minor avg FPS loss vs native D3D ⚠️ (translation tax — varies by game/GPU), higher minimums | Significant avg FPS loss, much lower minimums |

## 10. Usage Methods

### Proton (Automatic)

Proton ships DXVK + VKD3D-Proton bundled. No configuration needed — Steam
applies them automatically based on the game's D3D version. Valve updates them
with each Proton release.

### Lutris (One-Click Toggle)

- Per-game: Runner Options → "DXVK" / "VKD3D" / "DXVK-NVAPI" checkboxes
- Lutris downloads the release tarball, extracts DLLs, copies them into the
  prefix's `system32/`/`syswow64/`, and sets native DLL overrides
- See [lutris-deep-dive.md](lutris-deep-dive.md#dxvk--vkd3d-per-game) for details

### Manual Installation

```bash
# Download and extract
wget https://github.com/doitsujin/dxvk/releases/download/v2.7.1/dxvk-2.7.1.tar.gz
tar -xzf dxvk-2.7.1.tar.gz
cd dxvk-2.7.1

# Copy to wine prefix
export WINEPREFIX=/path/to/prefix
cp x64/*.dll "$WINEPREFIX/drive_c/windows/system32/"
cp x32/*.dll "$WINEPREFIX/drive_c/windows/syswow64/"

# Register DLL overrides
wine reg add 'HKCU\Software\Wine\DllOverrides' /v d3d9 /d native /f
wine reg add 'HKCU\Software\Wine\DllOverrides' /v d3d11 /d native /f
wine reg add 'HKCU\Software\Wine\DllOverrides' /v dxgi /d native /f
```

To verify DXVK is active: run the game with `DXVK_HUD=1` and look for the HUD
overlay with DXVK version info.

To remove DXVK: delete the DLLs and run `wineboot -u` to restore Wine's
builtin DLLs.

## 11. Why It's Not Used Here

The dotfiles environment runs on a **VMware SVGA II** virtual GPU, which has
**no Vulkan support**. DXVK and VKD3D-Proton require:

- A Vulkan 1.3 capable GPU
- Vulkan driver (Mesa RADV/ANV, NVIDIA vulkan, etc.)
- ⚠️ `vkquery` binary needed by `setup_dxvk.sh` for detecting Vulkan capabilities — not a runtime dependency; not relevant when DLLs are copied manually (see section 10)

The VMware SVGA II adapter provides only OpenGL 4.3 (via SVGA3D Gallium) and
has no Vulkan ICD. All DirectX games must go through **WineD3D** (OpenGL path):

```
Game → D3D API → WineD3D → OpenGL → Mesa SVGA3D → vmwgfx → GPU
```

This is substantially slower than the DXVK path would be, but it's the only
path available. If Vulkan were available, DXVK would be the first optimization
step (as noted in [freelancer-setup.md](../guides/freelancer-setup.md) and
[proton-deep-dive.md](proton-deep-dive.md)).
